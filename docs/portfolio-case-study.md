# Toss Invest Auto Terminal — Portfolio Case Study

## 한 줄 소개

토스증권 Open API 기반 자동매매를 실제 계좌 수준의 장부, 주문 안전, 전략 검증, 운영 가시성까지 확장한 개인용 풀스택 트레이딩 대시보드입니다.

## 프로젝트 정보

| 항목 | 내용 |
| --- | --- |
| 기간 | 2026.06 ~ 진행 중 |
| 역할 | 요구사항 정의, 제품·전략 의사결정, 구현 검수, 실거래 피드백 |

| 운영 | JSON state, sidecar/NDJSON archive, rolling backup, Oracle VM/systemd |

## 시작한 이유

처음 요구사항은 SOXL, MUU, SNXX의 조건부 자동매매였습니다. 그러나 실제로 필요한 것은 주문 함수 하나가 아니었습니다.

- 같은 토스 계좌에 장기투자 종목과 봇 종목이 섞여 있었습니다.
- 소수점은 정규장 시장가만 가능하고 정수 주문과 매도 방식이 달랐습니다.
- 추천값, 비중, 뉴스, 실적, 연준 이벤트가 서로 어떤 영향을 주는지 설명이 필요했습니다.
- 컴퓨터나 핫스팟이 꺼지면 봇 상태와 기록이 사라져서는 안 됐습니다.
- 자동화가 설정을 바꿨을 때 사용자가 이유를 모르면 시스템을 신뢰할 수 없었습니다.

그래서 프로젝트의 목표를 "높은 점수의 전략"에서 "실제 돈을 다루는 설명 가능하고 복구 가능한 운영 시스템"으로 확장했습니다.

| 고민 | 진단 | 해결 |
| --- | --- | --- |
| 초보자가 설정 의미를 알기 어려움 | 기술 용어와 입력값이 첫 화면을 차지 | 현재 주문 잠금·장부·운용 종목·검증 상태를 먼저 보여주고 고급 영역은 접힘 처리 |
| 수동 보유와 봇 보유가 한 계좌에 섞임 | 계좌 총수량만 보고 팔면 수동 장기투자분까지 매도 가능 | `externalTrackedHoldings`와 봇 장부를 분리하고 매도량을 봇 보유량으로 제한 |
| 소수점 보유를 정수 주문으로 매도 시도 | 매수 옵션과 실제 보유 형태가 동일하다고 가정 | 체결 수량과 정수/소수점 여부를 보고 정규장 금액 주문과 정수 수량 주문을 분기 |
| 추천 점수가 100점에 포화 | 누적 수익률이 점수를 지배해 낙폭 차이가 사라짐 | Calmar, MDD, 승률, 표본을 반영한 비포화 위험조정 점수로 교체 |
| 안전장치를 넣으면 백테스트 수익이 크게 하락 | 전략 알파와 방어 로직의 효과가 한 숫자에 섞임 | `alpha`와 `guarded` 이중 백테스트로 기회비용과 낙폭 효과를 동시에 표시 |
| 외부 데이터 실패가 종목 제외로 해석됨 | `available=false`를 0점으로 처리해 MU 비중이 자동 0%가 됨 | 저장된 검증 결과로 폴백하고 기존 비중 보존, 실제 오류 문구와 변경 출처 기록 |
| 체결되지 않은 수량이 이익으로 잡힘 | 봇 보유보다 큰 수동 매도를 원가 0의 봇 매도로 재구성 | `effectiveQuantity=min(매도량, 봇 보유량)`으로 회계 처리하고 초과분은 unmatched로 감사 기록 |
| 설정과 이력이 네트워크 재접속 후 초기화 | 메모리 상태와 디스크 저장, 긴 트레이더 틱이 경쟁 | 저장 큐 직렬화, 필드 소유권 분리, 10분 rolling backup, 손상 시 최신 백업 복구 |
| Toss 요청 한도 초과 | 모니터링, 버튼, 추천이 같은 API 예산을 공유 | API 그룹별 limiter와 reset 타이머, 버튼 disable, 요청 비용 미리보기, 추천 외부데이터 캐시 |
| 뉴스와 실적이 화면에만 있고 매매와 분리 | 정보 표시와 주문 예산 계산 경로가 달랐음 | 뉴스·경제 캘린더·실적 위험을 신규매수 차단 또는 예산 배율로 전략 평가에 연결 |
| 자동화가 보유 중 전략을 갑자기 변경 | 진입 기준과 청산 기준의 버전이 달라질 수 있음 | 기능별 자동화 스위치와 보유 종목 전략 변경 보류, 적용 이력과 이유 표시 |

## 가장 중요했던 기술적 결정

### 1. 실주문 이중 잠금

서버의 `LIVE_TRADING=true`와 웹의 `실제 주문 허용`이 동시에 켜져야 실제 주문을 보냅니다. UI 조작 실수나 배포 환경변수 실수 하나만으로 주문이 나가지 않게 했습니다.

### 2. 계좌 잔고가 아닌 봇 장부를 주문 기준으로 사용

토스 계좌의 실제 보유량은 체결 가능 여부를 확인하는 상한이고, 봇의 손익과 자동매도는 봇이 만든 체결만으로 계산합니다. 사용자가 직접 산 수량은 계좌 화면에는 보이지만 봇 포트폴리오 성과에는 포함하지 않습니다.

### 3. 추천을 투자 예언이 아닌 비교 도구로 재정의

초기에는 높은 수익률 조합이 100점으로 쉽게 포화됐습니다. 이를 위험조정 점수, 학습/검증 분리, 비용 추정, 최소 개선폭으로 바꾸고 점수를 "좋아 보이는 숫자"가 아니라 후보 설정 간 비교 지표로 제한했습니다.

### 4. 운영 상태와 분석 데이터를 분리

`state.json`은 빠른 복구를 위한 작은 운영 상태로 유지하고, 수 MB의 판단 샘플은 sidecar와 append-only NDJSON으로 분리했습니다. 봇의 15초 저장 주기가 무거운 학습 데이터를 매번 복사하지 않게 했습니다.

### 5. 자동 변경에는 반드시 출처를 남김

수동 저장, 전체비중 추천, 백그라운드 자가판단, 종목 OFF를 같은 변경으로 보지 않습니다. `lastAllocationChange`와 추천 이벤트에 이전값, 이후값, 원인, 점수, 자동/수동 출처를 기록하고 카드에 바로 보여줍니다.

## 전략이 발전한 과정

### 단계 1 — 레버리지 ETF 중심 MVP

SOXL, MUU, SNXX를 동일한 모멘텀 엔진으로 평가하고, 조건을 통과한 종목끼리 비중을 재분배했습니다. 소수점 주문과 정규장 제한, 손절·익절 라인을 먼저 구현했습니다.

### 단계 2 — 종목별 파라미터와 정밀추천

상품별 변동성과 추세 속도가 다르다는 문제 때문에 이동평균, 모멘텀 기간, RSI 범위, 손절·익절, ATR, ADX를 종목별로 분리했습니다. 추천은 외부 일봉을 이용해 Toss 요청 한도와 분리했습니다.

### 단계 3 — 실제 체결에서 회계·갭 위험 발견

실제 주문 사이클에서 명목 손절보다 큰 갭 손실, 부분·소수점 체결, 수동 주문 복구, unmatched sell 문제가 드러났습니다. 체결 상세 동기화와 봇 장부 재구성을 보강하고, 잘못 과대계상된 실현손익을 교정했습니다.

### 단계 4 — 점수와 안전장치 교차 검증

수익률 중심 100점 문제를 위험조정 점수로 바꾸고, 안전장치 없는 전략과 실제 방어 포함 전략을 동시에 측정했습니다. 안전장치가 수익을 줄이는 경우도 숨기지 않고 `guardImpact`로 표시했습니다.

### 단계 5 — 상품과 레짐 재검토

레버리지 갭과 휩쏘를 파라미터만으로 해결하기 어렵다는 결론에 따라 1x 종목과 QQQ 벤치마크를 도입했습니다. GLD, XLE, PPA, IEF, 인버스 ETF 후보는 여러 레짐에서 교차 백테스트했고, 재현되지 않는 결과는 문서에 반론까지 남겼습니다.

## 운영·신뢰성 설계

- 15초 트레이더 루프와 UI 저장을 같은 직렬 큐로 처리해 lost update를 방지했습니다.
- 현재 상태가 손상되면 최신 정상 백업을 자동 복구합니다.
- 판단 샘플은 working set과 영구 아카이브로 나누어 장기 분석 근거를 보존합니다.
- Toss API는 인증, 시세, 계좌, 주문 그룹별로 한도를 계산하고 429 응답을 재시도합니다.
- 서버 공인 IP를 UI에 표시해 Toss 허용 IP 변경을 바로 처리할 수 있습니다.
- Oracle VM에서는 `systemd`로 단일 인스턴스를 유지하고 데이터 디렉터리를 앱 코드와 분리합니다.

## UI/UX 결정

처음 화면은 "무엇을 설정할 수 있는가"보다 "지금 실제 주문이 가능한가"를 먼저 답합니다.

- 주문 상태, paper/live 장부, 실제 배정 종목, 검증 상태, 다음 행동을 운영 요약에 배치
- 설정 필드마다 초보자용 설명과 켜기/끄기 추천 표시
- 뉴스, 경제 캘린더, 상세 전략, 요청 한도는 기본 접힘
- 차트에 매수가, 1차익절, 최종익절, 손절선을 표시하고 라벨 겹침을 피하도록 배치
- 처리 시간이 긴 추천은 진행 상태와 완료/실패 토스트를 표시
- 데스크톱 3열 종목 카드를 모바일 1열로 재배치하고 가로 스크롤 제거

## 검증 방법

- `node --check`로 서버, 전략, UI 스크립트 문법 검사
- 격리된 `DATA_DIR`와 모의 Toss API로 API endpoint smoke test
- 실제 `/api/state`에서 연결, 장부, 신호, 자동화 이력 확인
- 데스크톱과 390px 모바일에서 렌더링, overflow, 콘솔 오류 확인
- 백테스트 결과를 서로 다른 구간과 파라미터로 재현하고 Codex·Claude가 반론 교차 검증
- 라이브 주문 변경은 코드뿐 아니라 체결·주문 이벤트와 운영 state까지 함께 감사

## 결과와 배운 점

이 프로젝트의 성과는 "자동매매로 수익을 보장했다"가 아닙니다. 실제 주문에서 전략보다 먼저 장부 정확성, 갭 위험, 데이터 실패, 요청 한도, 운영 복구가 중요하다는 점을 코드로 해결했습니다.

특히 다음을 배웠습니다.

- 백테스트 점수가 높아도 거래 비용, 레짐, 갭, 표본이 다르면 실전 성과가 달라집니다.
- 안전장치는 항상 수익과 손실을 동시에 줄이지 않습니다. 기회비용을 별도 지표로 봐야 합니다.
- 금융 자동화에서는 "왜 주문하지 않았는가"도 체결 이력만큼 중요한 데이터입니다.
- 자동화가 설정을 바꾸는 순간부터 변경 출처와 되돌릴 근거가 제품 기능이 됩니다.
- 실제 계좌 시스템은 신호 정확도보다 회계 불변식과 복구 가능성을 먼저 검증해야 합니다.

## 이력서용 요약

### 한국어

- 토스증권 Open API 기반 미국주식 자동매매 대시보드를 설계·구현하고, 조건 평가부터 주문·부분체결 동기화, 봇 전용 장부, 모바일 운영 UI까지 end-to-end로 구축했습니다.
- 수익률 중심으로 포화되던 백테스트 점수를 Calmar·MDD·승률·검증구간 기반 위험조정 점수로 재설계하고, 전략 알파와 안전장치 영향을 분리한 dual-backtest를 도입했습니다.
- 실계좌 운영에서 발견한 수동/봇 보유 혼재, unmatched sell 손익 과대계상, 외부 데이터 실패로 인한 비중 0%, 저장 race condition을 진단하고 회계·영속성 불변식으로 해결했습니다.
- API 그룹별 rate limit, 추천 캐시, 공인 IP 안내, 실주문 이중 잠금, systemd 단일 인스턴스 배포를 적용해 운영 안정성과 감사 가능성을 높였습니다.

### English

- Built an end-to-end automated trading dashboard on the Toss Invest Open API, covering signal evaluation, fractional and whole-share orders, partial-fill reconciliation, bot-only accounting, and responsive operations UI.
- Reworked an over-optimistic backtest score into a risk-adjusted metric using Calmar ratio, drawdown, win rate, validation splits, and a dual alpha-versus-guarded comparison.
- Diagnosed and fixed production-grade accounting and state issues, including manual-versus-bot holdings, unmatched sell P&L inflation, allocation changes caused by transient data failures, and concurrent state overwrite races.
- Added grouped API rate limiting, recommendation caching, double-gated live orders, auditable automation history, and single-instance VM deployment support.

## 면접에서 설명하기 좋은 포인트

1. 왜 계좌 보유량과 봇 장부를 분리했는가
2. 왜 높은 백테스트 점수를 그대로 신뢰하지 않았는가
3. 안전장치의 효과와 기회비용을 어떻게 분리 측정했는가
4. 긴 트레이더 작업과 웹 저장 사이의 race condition을 어떻게 막았는가
5. 외부 데이터 실패를 투자 판단 실패와 어떻게 구분했는가
6. 실제 손실·체결 데이터를 보고 상품과 전략 가정을 어떻게 수정했는가

## 한계와 다음 단계

- 일봉 중심 전략은 장중 갭과 급변 체결가를 완전히 예측하지 못합니다.
- 뉴스 감성 및 거시 방향 판단은 규칙 기반 휴리스틱이며 시장 해석을 보장하지 않습니다.
- 현재 종목군은 상관관계가 높을 수 있어 포트폴리오 단위 상관·리스크 패리티 검증이 더 필요합니다.
- 실제 성과 검증에는 더 많은 독립적인 paper/live 사이클과 장기간의 out-of-sample 데이터가 필요합니다.
- Oracle 배포 전 키 재발급, 사설 접속 경로, 모니터링·알림, 장애 복구 훈련이 필요합니다.
